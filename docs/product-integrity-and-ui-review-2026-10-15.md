**CourseHub 功能闭环与页面体验审视 · 2026-10-15**

审视基线：`dev1.1` / `9dece9caef1752a680f21bf5525804e9e7523008`。本轮交付建议和证据，没有修改业务代码、提交或部署。

结论：现有课程、资料、社交、积分和账号模块已形成应用框架；账号恢复、好友关系和私聊已有较完整的前次验证。当前最值得投入的是列表正确性、资料审核生命周期、跨模块上下文，以及手机端的信息层级。建议先完成这些整改，再安排部署。三套主题和既有组件体系可以继续使用。

**本轮检查怎样进行**

- 对照需求规格说明书、2026-10-08 审查台账、后续账号与私聊设计，检查当前路由、页面、接口、服务和 SQL。旧台账的账号恢复、私聊和好友关系问题已在后续开发完成，不能继续列为当前缺失。
- 启动既有独立本地 MySQL / Spring Boot / Vite 测试环境，用学生和管理员账号浏览。取得 55 份页面组合截图，覆盖桌面 1440px、窄屏 390px，以及代表页面的蓝、酒红、黑三主题；另外保留登录和问题复现截图。
- 针对翻页、迟到响应和接口失败使用浏览器 HTTP 夹具；审核资料权限与资料返回字段使用真实本地 API。夹具没有修改业务数据库。
- 本轮没有重复前次整套后端、账号恢复和私聊测试，没有要求用户重新做手机测试。页面能显示不等于整条业务流程已重新验收。
- 截图均为桌面 Chromium 渲染；本轮不增加 iPhone/Safari 或其他手机真机通过声明。既有手机验收范围见 `private-chat-mobile-acceptance.md`。

证据等级：**实测**表示当前浏览器或本地真实 API 可复现；**夹具复现**表示真实前端在受控 HTTP 数据或时序下复现；**源码确认**表示已追踪控制流/SQL，但本轮未执行相应写操作；**产品建议**需要在设计阶段明确取舍。

**需要同步处理的数据和产品细节**

- 退款后，订单列表和详情只改变订单状态，没有使用后端返回的 `score_balance` 更新用户 store。直接进入商城可能仍拿旧余额判断“积分不足”；进入个人中心才会重新取用户信息。本轮为源码确认，应在修复时补“取消→直接进商城”的验证。
- 个人中心“本月获得/消耗”从前 100 条积分流水在前端计算，超过 100 条会少算；“本月活跃”统计来源描述种类，不等同于活跃天数或次数。建议由汇总接口返回确定口径，或使用更准确的名称。
- 积分不足分支的提示写有“每日签到、学习课时、分享内容”奖励，但当前奖励写入主要是评价和资料审核；没有这些操作的完整业务入口。该分支又受禁用按钮限制，不一定可点到。建议展示可实际执行的赚分方式，并提供入口。
- 关于页复制 `support@bugaoshan.com`，客服页展示 `support@bugaoshan.edu`；两个地址还未证明是实际有人处理的渠道。应统一配置，优先引导已有的反馈表单，避免用户等候一个无运营保障的邮箱。
- 下载记录虽能看消耗与时间，但没有回到资料/再次下载的动作；举报表的资料 ID 也没有检查入口。历史记录应能把用户带回相关对象，并妥善显示已删除/下架状态。

**先明确的三项产品边界**

| 议题 | 当前事实 | 建议 |
| --- | --- | --- |
| “选课”是什么 | 目前更接近课程发现与个人选课清单；没有完整教务系统的容量、选课时段、冲突、先修规则和最终名单确认 | 首版明确为选课辅助工具，界面说明是否影响学校正式选课；若要正式选课，单独设计业务规则和教师/管理操作 |

| 兑换怎样交付 | 支持实物/虚拟/服务分类，但主要表现为扣积分和订单完成，没有统一领取/交付/核销资料 | 为首版选择明确的交付方式，例如校内自提并展示地点、时段与领取凭据；虚拟和服务分别定义交付结果。无需一开始增加完整物流系统 |

**建议的实施顺序与验收方式**

| 批次 | 范围 | 收口条件 |
| --- | --- | --- |
| A 正确性与反馈 | 课程表单错位、积分/订单翻页、管理端分页、搜索迟到响应、返回状态、错误页、主题选中态、缓存说明与清理 | 每个已确认问题有一个先复现后通过的聚焦回归；21/40/51 条数据、失败和快速筛选可以正常操作 |
| B 资料与跨模块闭环 | 审核检查、驳回编辑重提、公开上传者与收藏 DTO、课程关联跳转、举报处理结论；统一通知项的实际范围 | 用上传者、审核员、普通用户完成一次上传到通过、一次驳回修正，以及一次举报处理回看；普通用户不能获得待审文件 |
| C 高收益页面重排 | 手机登录、个人中心、广场和首页；同步课程/资料的主次操作与后台布局 | 针对这几页先给出结构稿，再实施；检查首屏任务、三主题状态和桌面/窄屏恢复 |
| D 发布前收尾 | 汇总实际完成范围，补真实邮件收件与部署环境检查，形成升级和回退记录 | 明确已测、未测和延后项后再决定部署 |

实际实施应按批次收口。不要把所有页面重做和新功能混成一次大改；每批跑受影响的自动用例，真机只抽查确实受影响的关键动作，避免重复之前长时间的手动验收。
