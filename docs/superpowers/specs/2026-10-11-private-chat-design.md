# 好友关系与可扩展私聊设计

日期：2026-10-11

状态：用户已于 2026-10-11 确认设计及 UI 交互稿，进入实施计划编写；尚未实现私聊产品代码。

## 目标与已确认范围

账号安全与密码找回已完成并同步至 `dev1.1` 的 `f6ebb7c`。本批让已建立好友关系的高校师生在 CourseHub 内进行一对一文字交流，并补齐作为发消息权限依据的好友关系一致性。用户已认可好友私聊、历史分页、未读数、发送重试去重，以及删除好友后保留只读历史的范围，并要求为后续能力留出扩展位置、设计与现有整体风格一致的 UI。

成功标准是：两位好友能够从通讯录开始聊天，消息持久化并在另一会话中刷新显示；只有会话双方能读取历史；关系解除后不能发新消息；改密导致旧访问与刷新凭据失效；桌面和手机在瓷白墨蓝、暖白酒红、曜石黑主题下保持现有导航、字体、卡片和按钮风格。

首版交付纯文本消息。附件、图片、语音、群聊、撤回、编辑、引用、在线状态和外部消息推送作为后续能力，通过下述明确边界扩展，不在首版提供尚无服务能力的按钮。管理员身份不授予私聊阅读权限。保留历史指双方在各自账号仍可正常登录时继续读取，不提供消息永久删除功能。

本批只准备增量迁移并在独立测试库验证，不迁移现有业务库，不配置真实 SMTP 或部署。

## 现有代码与方案选择

- `ContactController` 已有申请、接受、撤回/拒绝/删除、好友列表和名片接口。当前申请未校验目标是否可用，反向已接受关系可能产生另一条申请；接受 SQL 未限定待处理状态；方向唯一约束不能阻止同一对用户出现双向记录。私聊鉴权依赖这些规则，需一起修复。
- `ContactCardPolicy` 已统一联系人可见性。聊天 DTO 只返回最小身份资料，不复用实体的完整序列化，也不额外披露手机号、联系邮箱、找回邮箱、学号或隐藏实名。
- 现有访问与刷新 JWT 已核对 `credential_version`；前端请求层已有刷新、退出和会话身份检查。私聊继续使用这条链路。
- 前端为 Vue 3 / Element Plus / Pinia。`variables.css` 已定义三种主题和布局变量，`PageHeader`、`PageContainer`、`AppLayout`、`EmptyState`、`ErrorState`、全局按钮与输入样式可以复用。
- 原始 Story 的“发送消息”指跳转微信，仓库没有站内消息存储或私聊页面。本设计落实本次新批准的站内私聊，不把旧文档视为已实现站内消息。

推荐首版使用 REST + 可见页面短轮询：与现有认证和请求层一致，容易验证权限与重试，在增加实时推送时保留持久化 API。SSE 可在后续提供单向消息提示，但仍需处理长连接认证和断线补偿；WebSocket 可进一步支持双向实时事件，但当前会增加连接生命周期、重连和多实例分发工作。首版不引入新的产品依赖。

## 模块边界与扩展位置

| 模块 | 首版职责 | 扩展方式 |
| --- | --- | --- |
| `FriendRelationshipService` | 规范好友状态变更、目标校验、用户对加锁、读取已接受关系 | 黑名单、拒收规则在关系策略中增加，不散落到聊天控制器 |
| `ChatConversationService` | 私聊会话创建/复用、成员鉴权、列表和读取游标 | 会话类型及成员表支持后续新增不同会话策略；群聊仍需单独设计权限与迁移 |
| `ChatMessageService` | 类型校验、限流、事务发送、幂等与历史分页 | 新增消息类型处理器、附件服务和消息操作，不让控制器解析附件细节 |
| `ChatSendRateLimiter` | 数据库中的账号发送额度 | 阈值配置化；后续可更换存储实现并维持限流契约 |
| `chatApi` / `useChatPolling` | REST 请求、取消、轮询与补拉 | 替换传输适配器为 SSE/WebSocket；历史、发送和读游标 API 保留 |
| `ConversationList` / `MessageTimeline` / `MessageComposer` | 列表、渲染、输入与状态各自负责 | 按消息类型选择渲染组件；输入工具区在有后端能力时扩展 |

业务层在消息提交成功后形成 `ChatMessageCreated` 领域事件，事件只包含会话、消息、参与者 ID 和序号，不包含消息正文。首版不注册外部发送器；轮询仍为事实来源。以后接入推送时增加提交后适配器；跨实例可靠投递需要独立 outbox 设计，不能把首版的内存事件声称为可靠消息队列。

## 好友关系与权限

### 关系规则

- 自己不能添加自己；目标必须存在、未删除且启用。学生、教师和管理员可作为普通用户交友。
- 一对用户最多一条关系，保留原 `user_id`（申请发起人）、`target_id`（接收人）语义和现有接口路径。申请只有 `PENDING(0)`、`ACCEPTED(1)` 两种有效状态；拒绝、撤回和解除删除关系。
- 同方向重复申请不创建新行。反方向待处理申请按现有交互直接接受；任意方向已接受均返回“已经是好友”。
- 只有接收人能接受待处理申请；条件更新必须同时匹配关系 ID、接收人和 `status = 0`。重复接受不再次变更。撤回、拒绝和解除只允许参与者操作，并核对受影响行数。
- 列表只出现同一用户对的一条关系；发送权限始终从服务端当前关系计算，不能由前端标签或会话创建时的状态决定。

### 会话规则

- 创建/复用私聊以及发送新消息均要求双方账号可用且当前为已接受好友。会话只能有指定的两个成员；客户端不能指定发送人或成员列表。
- 列表、历史、增量拉取和读游标更新均按当前用户的会话成员身份限定。非成员与不存在会话统一返回 404，不披露是否存在、另一方身份或消息数量。
- 删除好友不删除会话、成员或历史。两位成员可读取已有历史，服务端返回 `can_send = false` 和原因 `NOT_FRIENDS`。重新成为好友后复用原会话并恢复发送。
- 对方禁用或删除时禁止创建/发送；现有另一成员仍可读历史，界面显示“账号不可用”，不展示对方隐藏或已删除的资料。当前账号禁用仍由现有认证链拒绝。
- 写事务在锁定发送人后复核请求认证时捕获的凭据版本。版本只能来自过滤链校验后的服务端上下文；保持现有 `SecurityUtils` 用户 ID/角色读取兼容。改密先提交时，旧凭据不能继续写消息；发送先提交时消息有效，随后改密使旧请求失效。

## 数据结构与并发

MySQL 为唯一持久化事实来源；新表使用 InnoDB 和 `DATETIME(3)`，新消息时间由服务端 UTC 时钟生成并作为 SQL 参数传入，API 时间包含时区，UI 按用户本地时间显示。无需更改 Windows 时区、JVM 全局配置或旧表的时间语义。BIGINT ID 和消息序号在 JSON 中输出为十进制字符串，避免浏览器整数精度丢失。

| 表 | 字段与约束 |
| --- | --- |
| `friend`（增量） | 增加由 `LEAST(user_id,target_id)` / `GREATEST(...)` 生成的用户对列及唯一索引；不改变申请人方向 |
| `chat_conversation` | `conversation_id`、`conversation_type = PRIVATE`、`private_user_low_id`、`private_user_high_id`、`last_sequence`（初始 0）、`last_message_at`、创建/更新时间；类型及私聊用户对唯一 |
| `chat_conversation_member` | `(conversation_id,user_id)` 主键、`last_read_sequence`（初始 0）、加入/更新时间；`user_id,conversation_id` 索引支持成员列表。首版固定两个成员，后续可增成员设置 |
| `chat_message` | `message_id`、`conversation_id`、`sequence`、`sender_id`、`client_message_id`（UUID）、`message_type`、`content`（JSON）、创建时间；会话+序号唯一；发送人+客户端消息 ID 唯一；历史索引 `(conversation_id,sequence)` |
| `chat_send_rate_window` | 账号、窗口起点、窗口长度、已用数、过期时间；复合主键按账号+窗口标识唯一，清理过期窗口 |

`TEXT` 的 `content` 固定为 `{"text":"..."}`。首版请求 DTO 只接受 `message_type = TEXT` 和 `text`，不接受任意 JSON 结构、HTML 消息类型、未知消息类型或客户端时间。正文中的 HTML 标签字符只作为普通文字保存和显示。后续新增类型时同时增加后端校验、API 契约和前端组件，不能仅凭客户端传入类型启用。

正文允许换行，按 Unicode code point 限制为 1–2000 个，纯空白拒绝，换行规范化为 LF，保留正常空格；拒绝除换行和制表符以外的控制字符。客户端提示与服务端校验采用同一规则。消息用纯文本渲染，不自动解释 HTML/Markdown 或执行链接。

### 锁与事务

涉及关系、会话创建和消息发送的写操作统一按用户 ID 从小到大逐个锁定两位用户，再锁关系、会话、成员和限流窗口；不得在持有会话锁后获取用户锁。采用 `READ_COMMITTED`，事务内无外部网络调用。统一加锁方法由关系服务提供。

创建会话在已锁用户对并验证关系后查询/插入规范私聊用户对，同时插入两位成员；唯一索引是最后防线，两个并发创建只返回同一个会话。

发送事务先验证成员和可发送关系，再查发送人+`client_message_id`。相同会话、类型和规范化正文的重复请求返回同一已存消息，不再计额度；同一 ID 携带不同正文或会话返回 409。即使之前发送成功，当前已解除好友的重试也不能借幂等键恢复发送权限。

持有会话锁时增加 `last_sequence`，写消息和更新最后消息时间，原子提交。并发发送按会话序号串行，从而增量拉取不会跳过较早分配却较晚提交的消息。回滚不产生可见消息或已用额度。锁冲突、重复索引和事务回滚需要真实 MySQL 验证，不依赖仅有的 mock 或 H2 结论。

默认每账号每分钟 30 条、每小时 300 条新消息，通过数据库原子预留，多实例共享。请求按同一顺序锁定窗口；只计新消息，发送失败回滚额度。阈值通过 `app.chat` 配置，可在未来替换限流实现。过期窗口保留最多 48 小时后由定时任务分批清理。限流返回 429 和重试时间，不丢失输入。

### 读取与未读

历史默认最新 30 条，每次最多 100；用 `before_sequence` 向前翻页，用 `after_sequence` 取新增，两参数互斥。服务端响应按序号升序，并分别返回下一游标、`has_more` 和当前最高已提交序号；增量过多时连续补拉，不能直接把游标跳到最高序号。消息按序号/消息 ID 去重。

读游标只允许成员更新，服务端校验序号对应该会话中实际存在的消息，使用单调最大值更新，不能倒退或指向其他会话。前端只上报已加载并显示的序号；服务端不能验证用户是否真的看过屏幕。读取接口本身不标记已读。仅在会话处于可见页面、消息加载成功且滚到最新时提交读游标；浏览旧历史或隐藏页不自动清零未读。

未读数是 `sequence > last_read_sequence AND sender_id != 当前用户` 的消息数。首版使用有索引的聚合查询，不维护容易漂移的多处计数；列表和全局总数取数据库结果。将来缓存时仍以数据库为准。

## API 契约与错误

新增 `/api/chat/**` 使用现有认证链，响应采用现有 `Result` 包装和 snake_case DTO。禁止把实体直接作为接口返回值。

| 接口 | 输入/行为 |
| --- | --- |
| `POST /api/chat/conversations/private` | `{target_user_id}`；验证好友并创建/复用，返回会话及 `can_send` |
| `GET /api/chat/conversations` | `limit`（默认 30，最大 100）、可选 `cursor`；按最后活动时间和会话 ID 倒序，只列当前用户的会话；返回 `next_cursor` |
| `GET /api/chat/conversations/{id}` | 成员、最小对方身份、最高序号、读游标、未读数、`can_send`、`send_disabled_reason` |
| `GET /api/chat/conversations/{id}/messages` | `before_sequence` 或 `after_sequence`、`limit`；历史/增量游标分页 |
| `POST /api/chat/conversations/{id}/messages` | `{client_message_id,message_type:"TEXT",text}`；返回服务端消息；首发和幂等重试均返回相同业务成功结构 |
| `PUT /api/chat/conversations/{id}/read` | `{last_read_sequence}`；校验实际消息并单调更新，返回读游标和当前未读数 |
| `GET /api/chat/unread` | 当前用户全部会话的未读总数，不返回其他用户信息 |

会话 DTO 包含 `conversation_id`、`conversation_type`、`peer`、`last_message`（最小文本预览与时间）、`last_sequence`、`last_read_sequence`、`unread_count`、`can_send`、`send_disabled_reason`。`peer` 仅包含用户 ID、昵称（缺失时使用账号）、头像、角色和已公开的院系；头像字段统一为 `avatar_url`，该 DTO 不扩展现有联系人字段的可见权限。消息 DTO 包含消息 ID、会话 ID、序号、发送者 ID、客户端消息 ID、类型、类型化内容、时间，不返回用户完整资料。

会话列表游标编码最后活动时间及 ID，输入必须有界并校验格式；空会话用创建时间作为最后活动时间。新增消息改变排序，轮询刷新首页时重建列表首页/分页游标并保留正在查看的会话；不拿旧排序游标连续请求新排序结果。

400：输入格式/类型/长度/游标不合法；401：登录失效；403：成员身份合法但已无发送权限；404：会话不存在或非成员、目标不可用；409：幂等键冲突；429：额度不足。聊天专用异常映射使用对应 HTTP 状态及 `Result` 业务码，不全局改变现有 `BusinessException` 的响应契约；已有好友接口仍以现有业务失败结构表达申请已处理。轮询错误在页面内显示且有限退避，不能每 5 秒弹一次全局错误；新增请求配置允许后台轮询静默提示，但 401 的清理/跳登录仍走现有逻辑。

### 整体风格和入口

- 保留现有 CourseHub 品牌、主导航和五项移动 TabBar。顶部个人区新增独立“消息”图标与最多 `99+` 未读角标，不占用当前订单 Bell 的含义；个人菜单/个人中心补“我的消息”。窄屏优先保留消息和个人入口，主题切换可继续从设置操作，避免顶栏溢出。
- 通讯录的已接受好友名片增加“发消息”，好友列表的消息按钮阻止冒泡，原查看名片行为保持。未接受状态不显示可发送入口。

### 桌面布局（宽度至少 768px）

标题“消息”，副标题“和好友聊聊课程与学习”，右侧为“去通讯录”。其下是一张整体卡片，左侧 300px 会话栏，右侧弹性聊天区域；平板会话栏缩至 260px，避免正文拥挤。

会话栏包含搜索框和可滚动列表。搜索仅过滤已获取会话的可见昵称/账号，不做消息全文检索。每行呈现圆角头像、姓名、最后消息预览、时间和未读角标；选中态使用主题浅色填充及清晰边框，不依赖颜色单独表达。

聊天顶部呈现最小对方身份和“好友”标签、查看名片按钮。不会显示缺乏依据的“在线”“正在输入”或“对方已读”。时间线用日期分组，对方消息靠左采用浅色背景，自己的消息靠右采用主题主色与 `--color-on-primary`；气泡圆角 18px，正文可换行且长链接自动折行。自己的消息仅显示“发送中”“已发送”“发送失败，重试”，其中“已发送”表示服务端持久化成功。

输入区固定在聊天卡片底部，包含多行输入、字符计数和发送按钮，工具区结构允许未来增加附件/引用，但首版不放禁用占位按钮。Enter 发送、Shift+Enter 换行；输入法组合阶段 Enter 不发送。无内容、超限或请求处理中不能重复提交。发送失败保留气泡和原幂等 ID，提供重试；不自动重发任意失效请求。

### 手机布局（小于 768px）

`/messages` 显示会话列表；`/messages/{id}` 显示单个会话，隐藏列表及重复大标题，顶部有可触达的返回列表按钮。保留现有品牌顶栏；聊天详情隐藏底部 TabBar 为输入区腾出空间，列表页仍显示现有 TabBar。使用 `100dvh`、安全区及可视视口调整，使软键盘出现时输入区仍可见；时间线独立滚动，不让整个页面和列表抢滚动。

头像、返回、重试、发送等可操作目标至少 44px。320px 宽度也不产生页面横向滚动。读旧消息时收到新消息显示“有新消息”定位按钮，不强制跳到底部；初次进入、本人发送以及用户已在底部时才跟随滚动。向上加载历史保持滚动锚点。

### 状态、访问性与草稿

- 空会话列表：说明“还没有会话”，提供去通讯录入口；好友空会话：说明“发送第一条消息”，输入可用。
- 初次加载显示骨架；网络失败显示重试区域，保留已有消息和草稿，不用空状态覆盖历史。
- 解除好友/对方不可用在聊天头下方显示原因条，输入区只读，历史仍可滚动。
- 会话不存在或无权限显示统一不可访问状态，不暴露其他成员。401 清空消息与草稿并回登录。
- 会话按钮有可读名称、选中语义和可见键盘焦点；输入有标签；消息列表使用低干扰的新增消息播报，不在补拉历史时重复朗读。尊重减少动画设置。
- 草稿按当前登录会话+会话 ID 保存在内存，不持久化消息/草稿到 localStorage；切换会话保留，退出、换账号、凭据失效立即清理。请求、定时器和迟到响应均绑定前端认证会话身份与当前会话请求序列。

## 轮询与前端生命周期

在已登录且页面可见时，每 15 秒刷新全局未读及当前会话列表首页；聊天详情每 5 秒拉增量并刷新发送权限。采用请求结束后再计时，不重叠轮询，卸载/隐藏/退出取消请求与定时器。隐藏页暂停，重新显示立即补拉；网络失败退避为 10/20/40/60 秒，成功恢复基础间隔。

只有一个应用级未读轮询所有者；聊天页面刷新不得重复开启全局计时器。切换账号或聊天对象递增请求序列，旧响应不能写入新会话。后续实时传输适配器发“需补拉”提示，仍以受鉴权的历史 API 补偿缺失消息，不能让推送成为绕过鉴权的正文读取通道。

## 增量迁移和验证

新增独立迁移、初始化表定义和运行说明。迁移先在测试库备份并检查：同一用户对重复关系优先保留已接受记录；若都待处理则保留最早 `friend_id`，其余删除并记录计数。自关系、孤立目标和非法状态应使预检查失败，不默默替用户处理；说明人工修复步骤。清理双向重复后再添加生成列与用户对唯一索引。迁移不会把已有好友自动创建为聊天会话，只有实际打开聊天时创建。

MySQL DDL 有隐式提交，迁移不能宣称整体事务回滚。部署顺序、备份及回退说明要明确；本次不在业务库执行。
