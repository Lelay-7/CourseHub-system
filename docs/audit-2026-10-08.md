# CourseHub 审查与完善记录

审查开始：2026-10-08；台账更新：2026-10-09  
范围：当前仓库源码、接口与数据库契约，以及首批修复的聚焦回归。线上服务和数据库未修改。

## 已确定的产品方向

- 保留当前布局和可切换的三套配色，后续调整具体页面的交互与细节。
- 登录账号独立且唯一；昵称可修改；学号、工号属于个人资料，修改昵称不改变登录凭据。
- 通讯录面向普通用户关系，支持加好友；私聊需要新增完整的服务端存储与界面。
- 密码找回采用真实邮件服务。个人资料中的联系邮箱不自动等同于已验证的找回邮箱。

| 设置页和通讯录的接口字段、异常和请求先后处理不一致 | 隐私保存不生效；搜索结果跳回旧关键词；失败被当成空列表 | 统一前后端枚举与字段；独立加载和失败重试；取消过期搜索结果；避免重复好友操作；统一“通讯录”名称 | `frontend/src/views/profile/SettingsView.vue`、`EditProfileView.vue`、`frontend/src/views/contact/` |

| 并发兑换先检查限额，之后才锁定商品 | 同时兑换可能绕过个人限购 | 先锁定商品行，再检查限额和扣减；保持商品到用户的加锁顺序 | `GoodsMapper.xml`、`MallServiceImpl.java` |

## 待完善的问题与功能

优先级含义：P1 为影响账号核心使用的缺失能力；P2 为明确的业务正确性或可操作性问题；P3 为较低影响的交互完善。新增能力与已确认缺陷分开标注。

| 编号 | 优先级 / 类型 | 已核实的事实与影响 | 建议处理 | 证据位置 |
| --- | --- | --- | --- | --- |
| A1 | P1 / 缺失能力 | 认证接口只有登录、短信、注册和刷新，用户接口没有修改密码接口。忘记密码和已登录修改密码尚无完整后端流程 | 先完成已验证的找回邮箱绑定、真实 SMTP、一次性验证码、找回和原密码修改；改密后使旧令牌失效 | `backend/src/main/java/com/bugaoshan/controller/AuthController.java`、`UserController.java` |
| A2 | P2 / 缺失能力 | 私聊没有消息、会话、已读状态的数据表和服务接口；当前好友模块不等于聊天功能 | 先做好友之间的文字私聊、历史消息和未读，再考虑附件及长连接 | `backend/src/main/resources/db/init.sql`、`backend/src/main/java/com/bugaoshan/controller/`、`frontend/src/api/` |
| C1 | P2 / 已确认缺陷 | `addFriend` 只排除自己，没有检查目标用户存在或是否禁用；好友表也没有用户外键。直接调用接口可生成无效目标的申请 | 增加目标存在、正常状态校验；定义禁用账号的搜索和好友交互规则 | `ContactController.addFriend`、`UserMapper.xml`、`init.sql` 的 `friend` 表 |
| C2 | P2 / 已确认缺陷 | 反向记录已是好友时，`addFriend` 没有拒绝；唯一约束只限制 `(user_id,target_id)`。B 接受 A 的申请后，B 再向 A 添加可产生第二条反向关系；并发双向申请也没有统一的关系约束 | 用无序用户对保持一份好友关系；将申请发起方向与关系状态分开；迁移前核查并处理旧重复关系 | `ContactController.addFriend`、`init.sql` 的 `uk_friend_direction` |
| C3 | P2 / 已确认缺陷 | `updateStatus` 只校验申请 ID 和接收者，没有限制旧状态为待处理。已接受关系仍能被再次“接受”；依赖 SQL 驱动的受影响行数时反馈也可能不一致 | 状态变更使用 `WHERE status=0` 的原子条件，并统一重复操作的业务反馈 | `backend/src/main/resources/mapper/FriendMapper.xml` 的 `updateStatus` |
| M1 | P2 / 已确认缺陷 | 管理员资料、订单、举报、广场和评价页没有分页控件，默认只请求前 20 条；课程、商品页固定请求前 50 条。数据超过这些数量后界面无法继续处理后续记录；用户管理页已有分页，不在此问题内 | 统一 `list/total` 返回与页码、筛选；给各管理页接入分页和失败重试。评价接口目前仅返回数组，需要补总数 | `frontend/src/views/admin/{MaterialAudit,OrderManage,ReportsManage,SquareManage,ReviewManage,CourseManage,GoodsManage}View.vue`、`AdminController.java` |
| M2 | P2 / 已确认缺陷 | `course_code` 全表唯一，软删除保留原代码；查重只查询 `is_deleted=0`。删除课程后用相同代码新建，预检查通过而插入触发唯一键，当前异常处理返回 500 | 先明确课程代码是否永久保留；按该规则查询包括已删除数据或提供恢复课程流程，并处理唯一键竞争 | `CourseMapper.xml.selectByCourseCode`、`init.sql` 的 `course.course_code`、`AdminController.createCourse`、`GlobalExceptionHandler.java` |
| D1 | P2 / 流程缺失 | 驳回资料的重新提交只把状态改回待审核并清空驳回原因；没有先修改资料说明或替换文件的接口。用户难以按驳回原因修正后提交 | 为本人已驳回资料提供编辑和替换文件，再重提；同时保留审核记录并处理旧文件清理 | `MaterialController.resubmit`、`MaterialServiceImpl.resubmitMaterial`、`MaterialMapper.xml.resubmitRejected` |
| U1 | P3 / 未完成的界面能力 | 课程通知、活动提醒、系统消息三个开关只读写 `localStorage.user_settings`，其它业务未使用这些值，也没有服务端通知偏好接口 | 接入实际通知机制后保存并执行偏好；在此之前不要让保存提示暗示通知投递规则已改变 | `frontend/src/views/profile/SettingsView.vue`；全仓对三个设置键的检索结果 |
| U2 | P3 / 已确认交互问题 | “清除缓存”调用 `localStorage.clear()`，同时清掉令牌、个人状态、主题和偏好。确认文案只说重新加载，没有告知会退出登录和重置配色 | 缓存按类别清理并保留登录与偏好；若提供清除全部数据，使用准确名称和说明 | `SettingsView.handleClearCache`、`frontend/src/utils/storage.js.clearAll` |

上述缺陷均依据当前源码与 SQL 契约确认。C2、M2 是按确定控制流和约束推导的可复现触发条件，此次没有在真实 MySQL 上写入测试数据。

## 后续推进顺序

1. 完成本批验证后先处理账号安全页：验证邮箱、忘记密码、修改密码、旧会话失效。这直接解决用户已经明确指出的登录与改密问题。
2. 修正好友关系模型和状态变更，再增加文字私聊。先保证一对用户只有一份关系，避免聊天权限、未读和会话列表建立在重复数据上。
3. 修复管理端分页、软删除课程代码的规则、驳回资料的编辑重提，逐页检查三主题下的反馈与窄屏布局。
4. 实现真实通知并完善缓存操作。每批保留对应回归检查和实际验证记录。

下一批账号功能的具体范围、用户流程、接口、迁移与验收见 [账号安全与密码找回设计](superpowers/specs/2026-10-09-account-recovery-design.md)，当前为待审阅方案。私聊将在好友关系规则明确后单独设计。

## 验证范围与限制

- 静态审查覆盖认证、用户资料、通讯录、课程与评价、资料、积分商城与订单、广场、管理端、设置以及相关请求和路由契约。静态覆盖不代表每一条业务路径和每个页面都已经完成实际操作。
- 本批聚焦回归检查使用真实前端请求拦截器和会话模块，在网络边界控制过期、失败、并发、切换账号和迟到响应；通讯录检查覆盖字段契约、搜索先后和操作保护。
- 后端测试覆盖认证、资料、通讯录、订单/兑换 SQL 与服务行为，以及实际 Spring Security 过滤链的 401/403 区分。模拟行锁测试不等于真实 MySQL 事务集成测试。
- 本地演示浏览器检查能验证渲染、路由和前端操作。使用 Mock 的页面不能证明真实短信、邮件投递、数据库持久化或线上登录已经可用。
- 未做线上数据库写入、生产部署、真实邮件/短信发送和完整多用户端到端测试。上线前还需在测试环境验证真实 MySQL 的并发与事务语义、账号迁移、邮件到达及两个真实账号的聊天权限。
